# Auto Timetable（タイテ作成ツール）

イベントの進行表を組み、当日の遅延・出演条件・時間短縮に合わせて調整案を比較する試作アプリです。Vinext / React、Cloudflare Worker、D1 / Drizzleを使用しています。

## リポジトリ

独立リポジトリは [GM7595/auto-timetable](https://github.com/GM7595/auto-timetable) です。ハッカソンの共有リポジトリから、このツールに関する履歴だけを引き継いで分離しました。インストール・起動・テストは、このリポジトリのルートで行います。

所有者のローカルにある `../DevDay Community Hackathon 2026-10-18/cue/` は、既存Sitesへの公開専用チェックアウトとして元の場所に残しています。このGitでは管理しません。このリポジトリの `.openai/hosting.json` はローカル開発用の設定だけを持ち、既存公開先のIDや秘密情報を含みません。既存サイトへ反映するときは、公開用チェックアウトのSite設定を維持してソースを同期します。リポジトリの分離によって公開サイト・データベース・シークレットは変更していません。

## 表示設定

ヘッダーの太陽・月・モニターのアイコンで、ライト・ダーク・端末に合わせるを直接選択できます。初期設定は端末に合わせるで、選択はブラウザ内に保存します。タイテやAPI設定には影響しません。

新しいイベントは上部の専用ボタン、イベント設定はイベント名の横の鉛筆、変更履歴はイベント情報の横から開きます。枠の追加とCSV・JSONの書き出しは進行表のツールバーにまとめています。

ヘッダーのカレンダーからイベント一覧を開きます。クラウド接続時はイベントごとに内容・履歴を保存し、新規作成しても前のイベントを残します。現在のイベントを全画面で共有するため、別タブで切り替えた場合は再読み込みしてください。保存中や比較中には切り替えません。

予定／進行中／終了は開催日・日本時間・タイテの開始終了時刻から自動表示します。転換・待機中は演目の進行中と区別します。端末時刻による表示で、実際の開始や終了を検知する仕組みではありません。時計の更新で保存データ・revision・固定条件は変更せず、遅れは変更欄から反映します。未反映プレビューは進行中扱いにしません。

## メンバーと楽器・役職

進行枠の編集画面でメンバーを追加し、1人に複数の楽器・役職を設定できます。Vo.（ボーカル）・Gt.（ギター）・Ba.（ベース）・Key.（キーボード）・Dr.（ドラム）をアイコンパレットから選択し、ホバーやキーボードフォーカスで正式名を確認できます。「部長」「司会」などはカスタム役職として追加できます。カスタム役職の絵文字は追加時に選べ、登録後も役職チップの絵文字から変更できます。候補以外の絵文字も直接入力でき、タイテ・比較プレビュー・CSV・JSONに引き継ぎます。楽器の既存候補は `lib/member-roles.ts` の一覧から追加できます。

担当は出演枠ごとに保存するため、同じ人が別のバンドで異なる楽器を担当できます。メンバー欄は「名前｜楽器・役職｜削除」の表形式で、名前左のつまみをドラッグして並び替えられます。マウスとタッチに対応し、移動先の線を確認して離すと順番が確定します。キーボードではつまみにフォーカスして Space／Enter でつかみ、矢印キーで移動先を選んで Space／Enter で確定、Escape でキャンセルできます。入力途中でもメンバー行を追加できますが、名前と楽器・役職に未入力のある行が残る間は保存できません。表全体の「役職なし」をオンにすると、その進行枠の全メンバーを名前だけで登録できます。役職欄は非表示になり、追加するメンバーにも同じ設定が適用されます。不要な空行は削除してから保存してください。「役職なし」への切替では全員の選択済み役職を解除します。

絵文字は `emoji-picker-react` の全カテゴリ・日本語データをサイトに同梱しています。日本語検索、最近使った絵文字、肌色バリエーションから選べます。端末のUnicode絵文字を使うため、外部画像CDNへのアクセスは不要です。

メンバー名と選択した役職はタイテの出演者欄、比較プレビュー、CSV・JSONに残ります。メンバー30人／枠、役職12件／人、名前160文字、役職40文字までです。同じ枠での名前の重複は受け付けません。

既存の `people` は準備時間チェック用の参加者名として維持し、任意の `members: [{ name, roles, roleNotRequired?, roleIcons? }]` を追加しています。`roleIcons` は選択済み役職名をキーとする絵文字マップで、未指定のカスタム役職は従来の🏷️を表示します。`members` がある場合は名前と順序が `people` に一致し、役職が1件以上あるか `roleNotRequired: true` であることを検証します。古い名前だけのイベント・保存済み提案もそのまま読め、編集時は「役職なし」として引き継ぎます。JSON内の任意フィールド追加なのでDBマイグレーションや既存イベントの書き換えは不要です。

## ローカル起動

Node.js 22.13.0以上を使用し、このディレクトリで実行します。

```sh
npm run install:ci
npm run build
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_omniscient_tenebrous.sql
npm run dev
```

開発画面は通常 `http://127.0.0.1:5173` です。実際のURLは起動時の表示を確認してください。ビルド済みWorkerの確認には `npm start` を使います。

ローカルDBは `.wrangler/state` に保存されます。適用済みのSQLは再実行しません。スキーマ変更時は `npm run db:generate` で新しいSQLを生成し、再ビルド後に未適用のファイルを順に実行します。この操作が変更するのはローカルDBです。本番への反映はSitesの公開手順で行います。

```sh
npm run build
npm run lint
npx tsc --noEmit
node --experimental-strip-types --test lib/planner.test.ts
node --test lib/decisions.test.mjs lib/agent-proposals.test.mjs lib/dots-instructions.test.mjs lib/proposal-review-link.test.mjs lib/page.test.mjs lib/timetable.test.mjs lib/theme.test.mjs
```

Sitesプラグインを使う場合は、そのインストール・プレビュー・ビルド・公開の手順に従ってください。

## 保存とAPI

D1の `cue_event_state` の `primary` 行が現在のイベントを保持し、`cue_saved_event` にイベント別の内容・履歴を最大100件保存します。新規作成・切替時は旧イベントの保存と現在の切替を同一トランザクションで実行します。既存データはそのまま一覧に含め、マイグレーションで書き換えません。初回の読み込みでサンプルイベントを作成します。画面は接続できない場合に端末内の保存へ切り替わり、保存先を表示します。端末内モードの一覧は現在の1件のみです。JSON / CSVの書き出しも利用できます。

| API | 入出力 |
| --- | --- |
| `GET /api/event` | `{ state, storage: "cloud", aiConfigured }` |
| `PUT /api/event` | 入力 `{ state, expectedRevision }`。保存後の `state` を返す |
| `GET /api/events` | `{ events }` にイベント名・日付・会場・時刻・枠数を返す |
| `POST /api/events` | `{ eventId, expectedRevision }` で保存済みイベントを開く。切替後の `state` を返す |
| `POST /api/plans` | 入力 `{ state, text }`。`{ plans, issue, engine, aiStatus, elapsedMs, notice?, decisions? }` を返す |
| `POST /api/decisions/check` | 合成データで実APIに接続し、`{ configured, aiStatus, decisions?, notice? }` を返す。イベント情報は送信しない |
| `GET /api/agent` | 現在のイベントへのエージェント提案を直近5件取得する。進行表は変更しない |
| `POST /api/agent` | 認可されたクラウドサービス向け。MCPと同じ `{ text, expectedRevision, requestId }` で提案だけを保存する |
| `PATCH /api/agent` | `{ action: "refresh" \| "dismiss" \| "restore", proposalId, eventId, expectedRevision }`。同じ提案の再比較・削除・元に戻す。タイテは変更しない |
| `GET /api/changes` | 現在のイベントの変更受付・未処理件数・イベント購読と通知状況を取得。読み取りでAI実行やタイテ更新はしない |
| `POST /api/changes` | `{ text, expectedRevision, requestId }`（UUID）で変更を受け付ける。タイテは未反映。購読先への通知は受付後に非同期配信 |
| `GET /api/status` | Decisionsの設定有無、MCPの提供状態を返す。dots本体の稼働は観測できないため `dotsConnected: null` |

保存時は `state.revision` と `expectedRevision` に同じ、読み込み済みのバージョン番号を指定します。サーバーが原子的に比較し、成功時に1増やします。競合時は `409` と最新の `state` を返し、後から来た変更で上書きしません。

JSONの大きさ・枠数・文字数・時刻・IDの重複などをサーバーで検証します。ブラウザからの更新と提案リクエストには同一オリジンの確認を行います。解釈できない依頼や成立する案がない依頼は、説明付きの `422` になります。

入力例：`いまの進行が10分押しています`、`次の登壇者が15分遅れます`、`ライトニングトークは16:10まで出演できません`、`全体を10分短縮したい`。自由な日本語を何でも解釈する仕組みではなく、対象と時間が明確な変更に対応しています。

## 進行表のルール

- 転換時間は各枠の直前に確保します。先頭枠には転換を加算しません。
- 完了・進行中・固定された枠の開始時刻は `fixedStart` で保持し、提案の保存後にも同じ時刻を再現します。
- 出演可能な開始・終了時刻、会場の音止め、終演時刻を検証します。休憩以外の枠は音止め時間をまたがず、枠全体を後ろへ移します。
- 出演者が連続する場合の準備時間などは注意点として表示します。手動編集で成立しなくなった条件も隠しません。
- 案APIは重大な制約違反がなく、保存後も同じ開始・終了を再現する案だけを返します。画面も制約違反がある案の反映を拒否します。

時間の正しさは通常のコードで検証します。候補生成は最大800候補の決定的な探索で、同じ入力から同じ候補を作ります。すべての並び順を探索する最適化や、観客の満足度を予測する仕組みではありません。

「全体を10分短縮」は、演目時間の合計ではなく、実際の終演時刻を10分早める目標です。音止め・固定開始・出演可能時刻によって削減が待ち時間に吸収される場合を考慮し、短縮の配分を探します。通常の短縮上限（休憩5分以上、予定中の演目は元の20%まで）と転換時間は守ります。「終演を16:40にしたい」も指定できます。目標達成が可能なら達成する案だけを返し、できない場合は最良の安全な代替案に不足分を表示します。有限探索のため、全解を調べた不可能性の証明ではありません。各案の `shortening` に目標・実際の短縮・内容の削減・不足・達成可否を分けて返します。個別の演目を指定した短縮は、その演目の所要時間を変更します。

## Decisions API

`OPENAI_API_KEY` がサーバーに設定されている場合、成立した案が複数あるときに、[Decisions API](https://developers.openai.com/api/docs/guides/decisions) の `gpt-6-luna` で有限の案IDから1つを選び、先頭に表示します。変更内容、出演者の準備、機材、メモ、構成を比較の材料にします。AIが時間制約を保証したり、新しい案を生成したりすることはありません。

キー未設定時は `engine: "rules"`、`aiStatus: "not-configured"` として動作します。拒否・タイムアウト・通信失敗・不正なIDの場合も、検証済みのルールによる順序へ切り替え、その理由を表示します。成立する案が1件だけの場合はAPIを呼びません。

「連携・保存」→「接続を確認」は、保存されたイベントを使わずに実APIへ小さな比較リクエストを送ります。キーの存在と接続成功を区別し、認証・権限・利用枠・レート制限・通信失敗を固定メッセージで表示します。実際に比較した場合はモデル名と所要時間、安全な診断情報を返します。上流のエラー本文や秘密情報は返さず、ログにも保存しません。キーを差し替えた場合は、新しい環境設定を反映するためSitesで再デプロイします。

設定名は `.env.example` に記載しています。実際のキーはSitesのサーバー用シークレットとして管理し、リポジトリやブラウザへ渡しません。キーがなくても進行表の編集とルールによる調整案は利用できます。

## dots / MCPと公開範囲

`POST /mcp` はJSON-RPCで、MCP `2026-07-28` の `server/discover`、`tools/list`、`tools/call` と、MCP Eventsの `events/list`・`events/subscribe`・`events/unsubscribe` に対応します。

- `get_event`：保存済みイベント・進行表・`pendingChangeRequests` を取得。
- `list_open_issues`：現在の制約違反・注意点を取得。
- `propose_change`：保存済みイベントへの変更案を取得。`applied: false` と元のバージョン、サイトで再比較する `reviewUrl` を返します。イベントや提案は保存しません。既存の入力形式・読み取り専用の権限は変更していません。
- `get_agent_context`：最新のイベント・revision・変更履歴・保存済み提案・`pendingChangeRequests`・操作範囲を取得。
- `publish_change_proposal`：`{ text, expectedRevision, requestId }` を受け取り、コードで検証・Decisionsで比較した候補を提案として保存。進行表には適用しない。

`publish_change_proposal` の提案はD1の `cue_agent_proposal` に保存されます。作成前・作成後・書き込み時に進行表のrevisionとイベントIDを検査します。同一イベントの同じrequestId・内容・revisionは再試行しても同じ提案を返し、内容の異なる再利用は409にします。上限はイベントごとに100件で、自動削除しません。画面には未削除の直近5件が表示され、15秒ごとと画面に戻った時に取得します。古い提案は「最新条件で再比較」から本文を引き継ぎ、サーバーで再計算して同じ提案IDの表示を更新します。新しいカードは追加しません。同じrevisionへの再試行も同じ比較結果を返します。元の受付・比較結果は残し、`cue_proposal_view` に再比較後の表示と削除状態を保持するので、元リクエストの再試行やdotの処理済み判定を壊しません。イベントrevisionと提案ごとのversionで競合を検査し、遅い比較が削除したカードを復活させることも防ぎます。

各カードのゴミ箱は提案を一覧から外し、「元に戻す」で復元できます。保存済みのタイテや演目は削除しません。「提案を確認」をもう一度押すと、調整案の×と同じく候補・表のプレビューを閉じます。比較中の各候補にもゴミ箱があり、その画面から候補を取り除けます。候補単位の削除は表示だけで、保存済み提案そのものを変更しません。

既存の3ツールしか見えないエージェントも、`get_event`・`list_open_issues`・`propose_change` で利用できます。`reviewUrl` はイベントID・revision・依頼テキストをURLフラグメントに持ちます。APIキー・認証トークン・候補そのものは含みません。依頼内容を含むリンクなので第三者への共有は避けてください。クラウドの最新イベントを取得し、同じイベントなら更新前のリンクでも `/api/plans` で自動的に再比較します。会話内で得られた案の復元ではなく、順位や候補は変わる可能性があります。処理済みフラグメントはURLから除去し、同じ画面で二重に実行しません。別イベント・不正なリンク・取得できない未来のrevisionでは比較しません。取得や比較の途中に状態が変わった場合も中止します。リンクを開いてもイベントや提案は保存せず、主催者が「反映」を押すまで進行表は変わりません。

### dots側の初回設定

1. サイトの「表示・連携設定」→「連携・保存」→「dotsへの指示をコピー」。
2. 自分のdotの会話に貼り付ける。Sitesが用意したこのサイトのプラグインを使用する。ツールが見つからない場合はそのプラグインを接続する。
3. dotが `get_event` と `list_open_issues` で現在のイベントを確認する。以後、主催者から変更連絡を受けたら `propose_change` で候補を比較し、返された「サイトで再比較」リンクを案内する。
4. 主催者がリンクを開き、サイトで新しく比較された候補を確認して反映する。追加の `publish_change_proposal` が利用可能な場合は、主催者が依頼すればサイトに提案だけを保存する運用も可能。その場合は「エージェントからの提案」から確認できる。

MCPツールはdots以外のエージェントでも使えます。MCPアクセスや提案の受信だけで「dots接続済み」「自動監視中」とは表示しません。dots本体で責任を割り当てる初回操作が必要です。外部メール・フォーム監視や定期実行は、対象と頻度の指定・必要な接続なしには開始しません。進行表の自動確定や第三者への通知機能もありません。これらを設定しない限り、dotsは会話で受けた変更連絡を処理する運用です。

### 変更受付ごとのイベント駆動

1. 「連携・保存」→「イベント監視の指示をコピー」をdotへ送り、`change_request.created` を現在の `eventId` に絞って購読させます。コピーやMCP接続だけでは購読は始まりません。dotから実際に登録された購読を確認してください。
2. サイトの変更欄へ入力し「dotに依頼」を押すと、D1の `cue_change_request` に保存します。UUIDの送信IDを再試行でも維持し、同内容は再受付しません。イベントとrevisionを原子的に検査し、上限100件で自動削除しません。
3. 受付イベントを署名付きWebhookで購読先へ通知します。通知の `data` はイベントID・受付ID・revisionだけで、依頼本文・演目・APIキーは載せません。1分ポーリングやブラウザを開いておく運用ではありません。Webhookの受領後、dotの作業は非同期に始まります。
4. dotは最新の `pendingChangeRequests` を読み、受付の `text` と供給された `requestId`（`change:`＋受付UUID）をそのまま使って `publish_change_proposal` を呼びます。最新revisionで条件を再検証し、候補のみ保存します。成功した提案保存を受付の完了として扱い、AI比較失敗・revision競合・不正な結果では未処理のままです。候補が1件のときはAPI比較を省略できます。
5. サイトの「エージェントからの提案」で主催者が確認して反映します。提案保存やタイテ編集は新しい受付イベントを発生させず、通知ループを防ぎます。

購読・配信状態はD1に保存します。購読者ごとのID、期限、署名付きcallback検証、鍵更新、冪等な購読解除と配信IDを扱います。callbackのURL・署名鍵はサーバー内部だけに保持し、画面や読み取りツールへ返しません。一般の任意URLへ安全にDNS固定接続する機能をこのWorkerでは提供しないため、callbackは厳格なHTTPSのChatGPT/OpenAI管理ドメインだけを許可し、リダイレクトや認証情報付きURLを拒否します。別ドメインのcallbackは対応範囲外として拒否し、汎用Webhookへの安全性を主張しません。接続解除そのものを独自に照会するAPIはないため、購読解除・期限切れ・通知先の応答・対象イベントの変更で停止を判断します。

画面の購読数はMCP Eventsの登録件数で、購読者がdotsであることの証明ではありません。通知の2xx受領も提案完了とは別です。実際のdotでの購読登録・通知受領・提案保存が確認できるまで、連携の本番動作確認は完了扱いにしません。ユーザー指定がイベント駆動のため、定期スケジュールへの自動フォールバックはしません。

公開先は所有者だけが利用する非公開Sitesを前提にします。ブラウザとMCPのアクセス制御にはSitesの認証境界を使い、イベント一覧と現在のイベントを共有します。ユーザー別のデータ分離や公開閲覧者向けの権限設計はありません。URLをコピーしても他の人へアクセス権は付与されません。公開時はD1の `DB` バインド、マイグレーション、MCP機能をSites経由で設定してください。
